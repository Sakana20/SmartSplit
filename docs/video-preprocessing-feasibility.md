# 批量视频预处理可行性讨论

## 文档目的

本文只讨论方案、边界和验收标准，不进入实现。

目标是对一批短视频做可复核的自动预处理：

1. 去除已经烧录在画面中的字幕，字幕位置不固定。
2. 去除开头的封面、静止插帧或其他异常短片段。
3. 降低“一秒内闪过多个画面”的跳切感。
4. 保留原始文件和完整诊断结果，无法可靠自动处理的片段进入人工复核。

这项能力与当前 FunASR 音频时间轴流程有关联，但职责不同。建议先作为独立的视频预处理阶段设计，输出无字幕、视觉节奏稳定的视频，再把音频或视频交给后续时间轴流程。

## 样例视频观察

样例：

```text
/Users/sakana/Desktop/Work/2026/6.29/淘宝闪购/素材/黄瓜/douyin_7633000832560360123.mp4
```

只读探测结果：

- 时长约 `31.9s`。
- 分辨率 `720x1280`，竖屏 `9:16`。
- 视频为 H.264，恒定 `30fps`，共 957 帧。
- 音频为 AAC，44.1kHz 双声道。
- 容器中没有独立字幕轨，字幕已经烧录进画面。
- 编码时间轴连续，没有证据表明问题来自文件层面的丢帧或可变帧率。
- 开头约 `0.13s` 处出现明显画面切换，首段很像封面或异常短插帧。
- 以较保守的场景变化阈值观察，全片约有 25 个明显切换点，很多镜头只持续约 `0.9–1.5s`。因此“跳帧”更准确地说是高频跳切或短镜头，而不是视频帧缺失。
- 字幕为白字黑边硬字幕。样例中多出现在画面上中部，但批处理方案不能依赖这个固定位置。

样例的开头异常帧容易自动识别；任意位置硬字幕可以处理，但很难承诺所有画面都能达到无痕修复；高频跳切可以检测，却需要先明确哪些镜头允许删除以及删除后怎样处理音频。

## 三类问题应分开处理

### 1. 开头固定帧或封面

建议检测视频开头的候选短片段，而不是固定删除前 N 帧。

可检查的判定信号包括：

- 开头至第一次强场景切换的持续时间。
- 片段内部的感知哈希、结构相似度和光流变化。
- 首段是否近似静止。
- 首段长度是否低于配置阈值，例如 `0.15–0.50s`。
- 首段与后续主体画面的视觉差异是否足够大。

输出候选区间、每项分数和最终决策。高置信度时自动裁掉；低置信度时保留并标记，避免误删正常的开场动作。

样例约 `0.13s` 的首段预计属于高置信度候选。

### 2. 任意位置硬字幕

由于不存在字幕轨，无法通过封装层直接删除。完整流程需要：

```text
抽帧
-> 全画面文字检测
-> 跨帧跟踪与字幕/场景文字分类
-> 生成逐帧文字掩码
-> 扩张掩码以覆盖描边和阴影
-> 时序视频修复
-> 闪烁、残字和误删检查
```

不建议把 OCR 识别结果本身作为唯一依据。去字幕只需要准确找到文字像素，文字检测和分割通常比“必须识别出正确文字”更重要。

需要区分：

- 后期叠加字幕：通常连续多帧出现、位置相对稳定、样式一致，应删除。
- 场景内文字：包装、电脑屏幕、门牌、日期牌等，通常属于原始画面，默认不应删除。
- 水印、账号、贴纸：是否删除属于另一项产品规则，不能默认等同于字幕。

推荐采用“文字检测 + 时序跟踪 + 字幕分类 + 视频修复”的组合。单纯逐帧图片修复容易在字幕区域产生闪烁；固定区域裁剪或模糊不满足“字幕可出现在任何地方”的要求。

可选修复路线：

| 路线 | 优点 | 局限 | 建议用途 |
| --- | --- | --- | --- |
| 固定区域裁剪/模糊 | 快、稳定 | 不支持任意位置，画面损失明显 | 不采用 |
| 逐帧图片修复 | 易搭建 | 容易闪烁、纹理漂移 | 原型或低运动画面 |
| 时序视频修复 | 连贯性较好 | 计算量大，遮挡和复杂运动仍可能失败 | 首选 |
| 邻帧内容传播 | 对静止背景很自然 | 背景被持续遮挡时没有可恢复信息 | 与时序修复组合 |

原则上，被字幕持续遮挡的原始像素已经丢失，任何方案都只能推断，不可能严格还原。可行目标应表述为“无可读字幕且修复区域无明显视觉破绽”，而不是像素级恢复原片。

### 3. 高频跳切或异常短镜头

这里需要避免术语混淆：

- 丢帧：编码时间轴或帧序列缺失。
- 闪帧：夹在正常镜头间、仅持续数帧的异常画面。
- 跳切：正常编码的视频被剪成很多短镜头。

样例主要是跳切，开头可能属于闪帧。三者不能使用同一条“补帧”规则。

建议先建立场景边界和镜头表，对每个镜头记录：

- 起止时间和持续时长。
- 与前后镜头的视觉相似度。
- 运动强度、模糊度和静止程度。
- 是否含字幕及其覆盖比例。
- 音频在边界处是否存在语音、节拍或明显瞬态。

只对满足明确规则的短镜头自动处理。例如：

- 数帧级异常插入，且前后属于同一镜头：删除异常帧，并用前后帧传播或插值恢复连续性。
- 开头或结尾的异常短镜头：直接裁切。
- 独立内容镜头持续不足阈值：只能在用户允许删减内容时删除。
- 正常但节奏快的多个镜头：不能凭“短”自动判为错误。

不建议用运动插帧把两个完全不同的镜头硬连起来。它通常会生成形变画面，也没有真正降低镜头切换频率。若删除完整短镜头，更自然的选择通常是硬切、极短叠化，或延长相邻镜头；具体策略应由用途决定。

## 建议的批处理架构

```text
输入扫描与探测
-> 标准解码和镜头检测
-> 开头异常段检测
-> 全画面字幕检测与时序跟踪
-> 跳切/闪帧分类
-> 生成处理决策清单
-> 视频修复与时间轴重组
-> 音频同步处理
-> 质量检查
-> 成品、报告和复核素材
```

建议把“检测”和“执行”拆开。第一遍只产生确定性的决策清单；第二遍按清单处理。这能让批量任务可复跑，也方便人工修改误判区间而不重新做全部分析。

每个视频至少保留：

- 原始媒体探测信息。
- 场景边界和镜头清单。
- 检出的字幕轨迹及逐帧掩码。
- 开头裁切候选及判定依据。
- 短镜头候选、分类和处置结果。
- 输出视频的时间映射表。
- 音视频同步诊断。
- 低置信度片段的联系表或预览视频。
- 处理配置、模型版本和运行日志。

## 音频与时间轴是关键约束

删除视频区间时必须同时决定音频如何处理：

1. **同步删除音频**：成片变短，口播可能丢字，但音画时间轴最清晰。
2. **只改视频、保留音频**：需要延长相邻画面或使用补画面，适合音频内容必须完整的场景。
3. **重建音频**：剪辑空间最大，但已经超出预处理范围。

如果后续还要用本项目生成字幕，所有裁切和删段必须输出旧时间到新时间的映射。否则原音频、ASR 时间轴和处理后视频会失去对应关系。

我的默认建议是：开头固定帧可同步裁掉对应音视频；中间短镜头默认不删，只标记。只有在确认“口播必须完整”还是“成片内容允许删减”后，才能确定自动消除跳切的执行策略。

## 可行性结论

### 高可行

- 批量读取和标准化视频。
- 检测并裁切样例这类极短开头封面/插帧。
- 建立场景边界、镜头长度和高频跳切诊断。
- 生成可复核的候选区间、掩码、联系表和 JSON 报告。
- 保持恒定帧率、音视频同步并输出时间映射。

### 中等可行

- 检测任意位置的常规后期字幕。
- 对背景简单、运动较小、字幕面积较小的画面做近似无痕修复。
- 自动区分绝大部分字幕与场景内文字。
- 识别并清除夹在同一镜头中的数帧级异常闪帧。

### 有明显风险

- 字幕遮挡人脸、手、商品边缘、反光、水流等复杂运动区域。
- 字幕很大、持续遮挡且邻帧没有露出背景。
- 字幕样式频繁变化，或与包装文字、水印混在一起。
- 自动删除“短但有意义”的正常镜头。
- 在不删口播音频的前提下，让大量高频跳切自然消失。
- 对所有批次承诺百分之百无残字、无修复痕迹、零误删。

因此适合采用“自动处理高置信度片段 + 低置信度人工复核”的流程，不适合第一版就做完全无人值守。

## 建议的第一阶段验证

先选取 10–30 条有代表性的视频建立小型评测集，覆盖：

- 字幕位于顶部、中部、底部和移动位置。
- 白字黑边、彩色字、半透明底板、花字。
- 人物、商品、桌面、户外、快速运动等背景。
- 开头静帧、短闪帧、正常开场。
- 正常长镜头、数帧异常插入和高频正常跳切。

第一阶段只做离线分析和候选标注，不直接批量覆盖成品。人工确认检测质量和处置规则后，再进入视频修复与重编码。

建议验收指标：

- 开头异常段：区间检测准确率、误裁率、边界误差。
- 字幕检测：逐帧掩码召回率、残字率、场景文字误删率。
- 修复质量：闪烁率、明显伪影比例和人工可接受率。
- 短镜头检测：召回率、正常镜头误删率。
- 输出完整性：音视频同步误差、恒定帧率、可播放性。
- 批处理能力：单条耗时、峰值显存/内存、失败可重试性。

第一版的质量门槛应优先压低误删和误裁，即宁可把不确定片段交给人工，也不要自动破坏有效内容。

## 开放问题

进入实现计划前，需要确认：

1. “无跳帧”具体是只删除数帧级异常画面，还是也要减少样例中约每秒一次的正常镜头切换？
2. 删除中间视频片段时，口播音频是否必须完整保留？
3. 若必须保留音频，允许采用哪种补画面方式：延长前后镜头、慢放、定格、素材重排，还是生成式补画面？
4. 水印、账号、贴纸和场景内包装文字是否也需要删除，还是只删口播字幕？
5. 输出必须保持原分辨率和 30fps 吗？编码格式、码率和可接受的画质损失是什么？
6. 是否接受少量低置信度片段进入人工复核，还是必须完全无人值守？
7. 批量规模大致是多少：几十条、几百条，还是每天持续新增？
8. 可用运行环境是什么：仅 Apple Silicon/MPS，还是有 NVIDIA GPU？
9. 后续字幕时间轴应基于原视频音频生成，还是基于预处理后的视频生成？

## 暂定决策建议

在开放问题确认前，建议采用以下默认方向：

- 不把视频预处理直接耦合进现有 ASR/forced alignment 核心模块。
- 第一阶段优先完成“检测、报告和人工复核闭环”，再开启自动修复。
- 开头高置信度异常段可自动裁切。
- 任意位置字幕使用全画面检测、时序跟踪和时序修复。
- 中间短镜头默认只标记，不自动删除。
- 所有时间轴变更都输出旧时间到新时间的映射。
- 所有处理都写入新文件，不覆盖原视频。
